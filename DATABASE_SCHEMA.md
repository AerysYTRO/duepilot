# DuePilot — Database Schema (Supabase / PostgreSQL)

Status: Phase 0 design. Each section maps to a migration file under `supabase/migrations/`.
Conventions: `uuid` PKs (`gen_random_uuid()`), `timestamptz` everywhere (UTC), snake_case, soft deletes only where audit requires (`invoices.voided_at`), money in **integer minor units** with ISO-4217 `currency char(3)`.

---

## 0. ERD (logical)

```
auth.users ─┐
            ├─ org_members ─ organizations ─┬─ clients ─ invoices ─ payments
profiles ───┘        │                      │        │
                     ├─ reminder_schedules ─┤        ├─ reminder_instances ─ reminder_deliveries
                     ├─ email_templates ────┘        └─ (lifecycle/payment status + overdue flag via triggers)
                     ├─ subscriptions (Stripe)
                     └─ csv_jobs / audit_log
```

Every tenant table carries `org_id uuid not null references organizations(id) on delete cascade`, is RLS-enabled, and has an index leading with `org_id`.

## 2. Clients

### `clients`
`id`, `org_id`, `name text not null`, `email citext` (billing contact), `cc_emails text[] default '{}'`, `phone text?`, `tax_id text?` (VAT/CUI/CNP), `registration_no text?`, `address jsonb?` (street, city, county, country, postal), `currency char(3)?` (override; else org default), `reminder_schedule_id uuid? → reminder_schedules` (client-specific default), `notes text?`, `archived boolean default false`, timestamps.
Unique: `(org_id, lower(name))` partial where not archived — prevents accidental duplicates; import dedupe relies on it.

## 3. Invoices & Payments

### `invoices`
| column | type | notes |
|---|---|---|
| id, org_id, client_id | uuid | client FK `restrict` if payments exist |
| number | text | per-org sequence: `INV-2026-0001`; unique `(org_id, number)`; generated by trigger from `invoice_sequences` |
| issue_date | date | |
| due_date | date | ≥ issue_date CHECK |
| subtotal_minor | bigint | ≥ 0 |
| tax_rate numeric(6,3) | | percent, default 0 |
| tax_minor | bigint | recomputed by trigger |
| total_minor | bigint | = subtotal + tax (CHECK keeps consistent) |
| paid_minor | bigint | trigger-maintained sum of payments, never > total (guard). **Partial payments are explicitly represented**: `0 < paid_minor < total_minor` ⇔ payment status `partially_paid`; each partial payment is its own immutable `payments` row |
| currency | char(3) | frozen at creation |
| lifecycle_status | text | `draft` \| `sent` \| `void` — **document lifecycle only** (see state model below) |
| payment_status | text | `unpaid` \| `partially_paid` \| `paid` — **derived from payments**, trigger-maintained, never set directly by clients |
| is_overdue | boolean | **derived lateness flag**, orthogonal to payment_status (a `partially_paid` invoice can be overdue). Refreshed by `mark_overdue_invoices`, evaluated against org-timezone "today" |
| notes / line_items jsonb | | line items stored as JSONB array `{description, qty, unit_minor}` |
| sent_at, paid_at, voided_at | timestamptz? | |
| created_by | uuid | audit |

**Invoice state model (three orthogonal dimensions — clarification approved in Phase 1 review):**

A single mutually-exclusive `status` column conflated document lifecycle, payment progress and lateness. The model is therefore split:

1. **Lifecycle** (`invoices.lifecycle_status`, client-transitioned, DB trigger guard):
```
draft → sent → void (terminal; admin+, audited)
draft → void
```
2. **Payment status** (`invoices.payment_status`, *derived only* from the `payments` sum by trigger — clients can never set it):
```
unpaid (paid_minor = 0) → partially_paid (0 < paid_minor < total_minor) → paid (paid_minor >= total_minor, terminal except audited reopen)
```
Partial payments are first-class: every recorded payment is an immutable `payments` row; `paid_minor`/`balance_minor` recompute on insert **and delete** (rollback correctness); `partially_paid` invoices keep receiving reminders for the remaining balance with `{{amount_due}} = total − paid`.
3. **Overdue flag** (`invoices.is_overdue`, derived, *not* a payment state): `lifecycle_status='sent' AND payment_status <> 'paid' AND due_date < today(org timezone)`. Evaluated by `mark_overdue_invoices` (cron + read paths). A partially-paid invoice can be overdue; a paid invoice is never overdue. UI badges compose all three (e.g. “Partially paid · Overdue”).

Guards (DB trigger `trg_invoice_guard` mirror of `core` state machine): no lifecycle change once `void`; `paid ⇒` lifecycle stays `sent` unless admin reopen (audited); reminder materialization/cancellation keys off `lifecycle_status` + `payment_status` (stop-on-paid = `payment_status='paid'` or void).

### `payments`
`id`, `org_id`, `invoice_id`, `amount_minor bigint check > 0`, `currency char(3)` (must equal invoice currency — trigger), `received_on date`, `method text check ('bank_transfer','card','cash','paypal','other')`, `reference text?`, `recorded_by uuid`, `created_at`. Deleting a payment re-runs the invoice recompute trigger (partial-payment correctness).

### `invoice_sequences`
`org_id`, `prefix`, `fy int`, `next_val int` — row-locked allocation inside number-generation function (race-safe).

## 4. Reminder Engine

### `reminder_schedules`
| column | type | notes |
|---|---|---|
| id, org_id | | schedule belongs to org; default schedule flagged `is_default boolean` |
| name | text | e.g. “Standard B2B” |
| offsets jsonb | | ordered array: `[{"days":-3,"stage":"before_due"},{"days":0,...},{"days":3},{"days":10},{"days":21}]` — negative = before due date, positive = after. CHECK: distinct days, −14…90 range, max 8 steps (plan-limited later) |
| template_id | uuid → email_templates | stage-specific template optional later |
| active | boolean | |

Validation lives in `core/schedule` (pure TS) *and* a SQL CHECK/jsonb schema function — defense in depth.

### `reminder_instances` — the materialized job queue
One row per (invoice × schedule step). **This is what makes delivery idempotent.**

| column | type | notes |
|---|---|---|
| id | uuid | |
| org_id, invoice_id | uuid | |
| schedule_id, step_index | | provenance |
| scheduled_for | timestamptz | UTC instant computed from due_date + org timezone at materialization time |
| status | text | `pending`,`sending`,`delivered`,`skipped`,`failed`,`cancelled` |
| attempts | int default 0 | max 5 |
| next_attempt_at | timestamptz | exponential backoff: 15m, 1h, 4h, 12h |
| claimed_at | timestamptz? | lease; reclaimed after 10 min if stuck in `sending` |
| idempotency_key | text unique | `sha256(invoice_id || step_index || template_version)` — DB-level duplicate-delivery guard |
| last_error | text? | |

Indexes: partial `(scheduled_for) where status='pending'`; `(invoice_id) where status in ('pending','sending')`.

**Lifecycle:**
1. Materialized when invoice becomes `sent` (`trg_materialize_reminders` calls `core`-mirrored SQL; DST-correct day-of-month anchoring done in SQL via `due_date + tz` cast arithmetic).
2. Re-materialized (old pending cancelled) when due_date/schedule changes; cancelled entirely when invoice `payment_status → paid` or `lifecycle_status → void` (stop-on-paid layer 2). Partial payments do **not** cancel reminders — remaining-balance steps continue.
3. Worker claims via RPC `claim_due_reminders(batch int)` — `FOR UPDATE SKIP LOCKED`, sets `sending`, returns rows. Unique idempotency_key + status guards make replays no-ops (layer 1). Manual sends reuse the same table with `step_index = -1`.

### `reminder_deliveries` — append-only log
`id`, `instance_id fk`, `org_id`, `invoice_id`, `attempt int`, `provider text default 'resend'`, `provider_message_id text?`, `to_email citext`, `lang text`, `template_id`, `status check ('accepted','bounced','failed')`, `error text?`, `delivered_at timestamptz default now()`.
Feeds **Reminder History** UI and analytics. No updates allowed after insert (RLS: select-only for members).

## 5. Email Templates

### `email_templates`
`id`, `org_id`, `key text` (e.g. `before_due`, `due_today`, `overdue_1`, `overdue_final`, custom), `lang check ('en','ro')`, `subject text`, `body_html text`, `body_text text`, `version int default 1`, `updated_by`, timestamps. Unique `(org_id, key, lang, version)`.
Placeholders whitelist rendered server-side: `{{client_name}} {{invoice_number}} {{amount_due}} {{due_date}} {{org_name}} {{org_link}}` — unknown placeholders rejected at save time (XSS/injection control, see SECURITY.md §6). Orgs without custom templates fall back to system defaults (`is_system boolean`, `org_id is null`, seeded per lang).

## 6. Billing (Stripe)

### `subscriptions`
`org_id pk→fk`, `stripe_customer_id text unique`, `stripe_subscription_id text unique`, `plan text check ('free','starter','pro','agency')`, `status text` (Stripe statuses mirrored), `current_period_end timestamptz`, `seats int?`. Written **only** by the webhook Edge Function. Plan limits (max clients/invoices/month, schedules, team seats) resolved in SQL view `org_limits` and enforced by triggers on insert — never client-side only.

### `stripe_events`
`id text pk` (event id), `type text`, `payload jsonb`, `processed_at` — webhook idempotency ledger.

## 7. Import / Export / Audit

### `csv_jobs`
`id`, `org_id`, `kind check ('clients_import','invoices_import','clients_export','invoices_export')`, `file_path` (Storage), `status check ('queued','running','completed','failed')`, `stats jsonb` (`{inserted, updated, errors:[{row, code, message}]}`), `created_by`, timestamps. Processing runs in the Worker (bounded batch, row-level validation via shared zod schemas); the SPA polls/subscribes for progress.

### `audit_log`
`id bigserial`, `org_id`, `actor uuid?`, `action text`, `entity_type text`, `entity_id uuid`, `meta jsonb`, `at ts default now()`. Records: membership changes, plan changes, invoice reopen/void, template edits, data export, GDPR erasure execution. Select-only via RLS to admins.

## 8. Views & Analytics

- `v_invoice_open`: open balance per invoice (`total_minor - paid_minor`) with `is_overdue` computed against org timezone.
- `v_org_kpis`: outstanding total, overdue total/count, collected this month, avg days-to-pay (payments.received_on − invoices.issue_date), reminder send counts by status. Dashboard reads these; all RLS-inherited (security_invoker=true).

## 9. RLS Policy Matrix (summary)

| Table | member select | member write | admin write | service_role |
|---|---|---|---|---|
| organizations | ✔ | name/logo/timezone via fn | ✔ (policy on role) | ✔ |
| org_members | ✔ (own org) | — | ✔ | ✔ |
| clients / invoices / payments | ✔ | ✔ | ✔ | ✔ |
| reminder_schedules / instances | ✔ | ✔ schedules | ✔ | ✔ (Worker) |
| reminder_deliveries | ✔ | ✗ (insert by Worker only) | ✗ | ✔ |
| email_templates | ✔ | ✗ | ✔ | ✔ |
| subscriptions / stripe_events | ✔ subs / ✗ events | ✗ | ✗ | ✔ |
| csv_jobs / audit_log | ✔ own jobs / admins audit | insert jobs | ✔ | ✔ |

All policies are of the form `using (is_org_member(org_id)) with check (is_org_member(org_id))` plus role gates — never `true`, never keyed on JWT claims alone. Cross-org access must be impossible even with a valid JWT of another tenant (tested in every phase's integration suite).

## 10. GDPR Notes
Personal data lives in: profiles, clients (contact fields), reminder_deliveries (`to_email`), csv files (Storage). Retention: deliveries log truncated to 24 months by scheduled cleanup; org deletion cascades; anonymization function `gdpr_anonymize_client()` available to admins. Details in SECURITY.md §8.
